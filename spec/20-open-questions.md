# Open questions

Part of the [XmlEssentials spec](README.md).

- **Docs hostname.** Not a spec concern. `PackageProjectUrl` is the GitHub repo. Docs pages that need a site URL use `(docs site TBD)`.
- **Package icon.** None. Not a release gate.
- **Lifetime of a decoded `ValueSpan`, and reader copies.** `Utf8XmlReader` is a struct, so `var lookahead = reader;` compiles and is the usual `Utf8JsonReader` look-ahead idiom. A value that needed decoding (an entity, a normalized line end, attribute whitespace) lives in a buffer the copy shares. Advancing either reader to another decoded value overwrites it, so the other reader's current `ValueSpan` changes underneath it. Undecoded values are slices of the input and are unaffected. This was already true for text; attribute values now behave the same way (they used to get an array each). Options: (a) specify it: a decoded `ValueSpan` is valid until this reader **or a copy of it** next advances; (b) allocate a fresh buffer for every decoded token, which is safe and costs an allocation per escaped value; (c) keep the buffer in a small shared object that records which token owns it, and re-decode on access when the owner differs. (c) is the only one that is both safe and cheap. Not decided; no test pins the current behavior.
- **Leading `+` on integers and decimals.** XML Schema allows it (`+5` is a valid `xs:int`) and the lexical routines now accept it. The earlier draft of [XML fidelity](02-xml-fidelity.md) rejected it on purpose. If the stricter rule was deliberate (for example to match what the writer emits), restore it in `XmlLexical` and say so in the departures table.
- **Fixture licensing.** Some fixture files are third-party content carried by the repositories they came from (MLB data, RSS feeds, James Clark's xmltest collection, Sun and IBM conformance tests). See `Fixtures/README.md`. Decide whether they may be committed to a public repository or should be fetched in CI.
- **UTF-8 attribute overloads.** `WriteAttributeString(ReadOnlySpan<byte>, ReadOnlySpan<byte>)` takes an unprefixed name only. A prefixed or namespaced attribute needs the `string` overloads, so a zero-allocation reader-to-writer copy cannot be written against the public surface (the DOM uses internal calls). Decide whether to add `WriteAttributeString(utf8Prefix, utf8LocalName, utf8NamespaceUri, utf8Value)`.
- **DOM `Deserialize` overloads are static methods on `XmlSerializer`.** In STJ they are extension methods on `JsonDocument` / `JsonElement` / `JsonNode` (`document.Deserialize<T>()`). [Serializer](07-api-serializer.md) lists them as statics. Decide which shape to ship; both can exist.
- **Typed values that only the serializer reads.** [Testing](14-testing.md) and `AGENTS.md` say typed values are parsed in `XmlLexical` only. `char`, `Uri`, `Version`, and enums are parsed in their converters, because the reader and the DOM have no getter for them and an enum parser is generic over the enum type. Either move the three non-generic ones into `XmlLexical` and add reader / DOM getters, or reword the rule as "one implementation per type".
- **The root name of an array.** *Settled 2026-11-24 ([decision 70](24-doc-findings-resolution.md)): every sequence is `ArrayOf` + item name. The rest of this entry is the question as it stood.* `Serialize(new[] { 1, 2 })` wrote `<Int32Array>` (the element type name plus `Array`), while `SerializeAsyncEnumerable<int>` wrote `<ArrayOfInt32>` and a `List<int>` wrote `<ListOfInt32>`. `Deserialize<int[]>` checks the root name, so it cannot read what `SerializeAsyncEnumerable<int>` wrote. Pick one name for a sequence of `T`, or make the array reader accept both. Not decided; `Int32Array_RoundTripsAsTheRoot` pins the current name.
- **The serializer reads a scalar element without a text token.** `Utf8XmlReader.TryReadLeafContent` returns the text of `<Id>42</Id>` and leaves the reader on the end tag, so no `Text` token is ever current for it. It is internal, and a public form would need a name and a contract (what it returns for white space, for CDATA, for an empty element). Not proposed yet.
- **The serializer relies on a decoded value surviving the end tag.** When a text or CDATA token needed decoding and the next bytes are `</`, the built-in converters parse the value from the reader's decode buffer after reading the end tag (`Utf8XmlReader.IsEndTagNext`), instead of copying it first. That is correct today because reading an end tag decodes nothing. It is one more reason to settle the lifetime question above; option (c) there must keep this property or the copy comes back.
- **A copy of a reader shares more than the decode buffer.** The element and namespace stacks beyond their inline slots, the attribute table beyond eight attributes, and the scratch buffer are shared by a reader and its copies. `Utf8JsonReader` copies are fully independent, and nothing in the reader's documentation says ours are not. The library's own two rewinds no longer depend on this: `Utf8XmlReader.TrySkip` and the serializer's skip-then-rewind (`TryReadWithReadAhead`) call `DetachAttributeStorage` on the reader that reads ahead, so the copy alone holds the start tag's attributes ([N8](24-doc-findings-resolution.md)); The `TrySkip_OnAPartialBlock_` tests in `Utf8XmlReaderResumeTests` and `AsyncEnumerable_AValueWithManyAttributes_KeepsThemWhenItsChildHasAsMany` pin them, including a skip from below the inline stack depth. What is left open is a copy a caller makes. A copy that reads past the end of the original's element at a depth greater than the inline stack still overwrites stack entries the original needs; that case is not pinned. Options: document the limit, or give a copy its own stacks the first time it writes to one.
- **A node that is not an element has no markup of its own.** `XmlElement.GetRawXml()` on an attribute returns an empty string, and `XmlNode.ToString()` on a text or CDATA node that is not inside an element throws `XmlException` ("... is not allowed at the document level"), because both write through a writer that expects a document. The tests now pin this (`Attribute_GetRawXml_AndBooleanDigits`, `Clone_CommentCDataPi` asserts cloned nodes by their values instead). `ToString()` validating is itself pinned by `NodeTree_PrefixWithoutNamespace`, so the fix is a fragment mode on the writer, not skipping validation. Not decided.
- **A member with no namespace takes elements from namespaces nobody named.** `[XmlElement("title")]` matches `<title>` in any namespace except one that another member gives the same local name ([decision 63](24-doc-findings-resolution.md)). So in a feed that adds `<dc:title>`, a type with `title` and `itunes:title` reads `dc:title` into `title`, and the last one read wins. `Namespace = ""` on the member says "no namespace, exactly" ([decision 74](24-doc-findings-resolution.md)): with it `dc:title` is not read into `title`. What is open is only the default, which is what makes a type work under any default namespace.
- **XPath: the open decisions of the design.** [XPath 1.0](27-xpath.md#open-decisions) is implemented as the design proposed for each: no convenience members on `XmlElement` or `XmlDocument`, no default for `MaxOperations`, no navigator over the mutable `XmlNode` tree, a plain (not pooled) parent table and name index, and the engine in the core assembly. Each is the owner's to settle.
- **XPath: the Native AOT smoke test on Linux.** `XmlAotPublishTests` looks for `CloudNimble.XmlEssentials.Tests.Aot.exe`, which only Windows produces, so it fails on Linux before it runs the program. Published and run by hand on Linux, the program passes, the XPath checks included, with no IL warning. Decide whether the test should use the file name of the platform.
- **What the test audit left open.** `Split_AtEveryByte_MatchesSinglePass` compares split reads with a single pass whose token list is checked only for holding a document element; the same is true of the `MustRead` documents, which are now also read at every split. Pinning those token lists by hand is the remaining work there.
